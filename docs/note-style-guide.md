# 单篇论文笔记写作规范

本规范用于保证仓库中的论文笔记既适合首次阅读，也适合数月后快速恢复记忆，并且便于 AI Agent 持续维护和横向比较。

## 1. 写作目标

一篇合格笔记应让读者不重新通读论文，也能回答：

1. 论文解决什么问题？
2. 为什么这个问题重要？
3. 作者真正新增了什么机制或观点？
4. 被更新的对象是什么，信息存在哪里？
5. 方法在训练时、测试时还是部署阶段工作？
6. 是否跨任务积累，是否更新模型参数？
7. 哪个实验最支持核心结论？
8. 证据不能证明什么？
9. 最大局限和失败模式是什么？
10. 与仓库中最接近的工作有什么差异？
11. 对后续研究或工程有什么可迁移启发？

笔记不是按论文顺序缩写，也不是摘要翻译。它应按照“以后重新理解这篇论文所需的顺序”重组内容。

## 2. 三层阅读结构

### 第一层：30 秒读懂

位于标题和简短资源链接之后，必须包含：

- 一句话总结；
- 文章性质；
- 核心问题；
- 核心机制；
- 更新对象；
- 学习阶段；
- 是否跨任务；
- 是否更新模型参数；
- 最重要结论；
- 最大局限；
- “不要误读”。

这一层不得先铺陈作者履历、完整投稿历史或公式。

### 第二层：10 分钟理解

包含：

- 论文定位；
- 研究问题与动机；
- 进化机制或分析框架；
- 核心方法；
- 实验设计；
- 主要结果；
- 创新、局限和相关工作。

### 第三层：按需查阅

包含：

- 关键公式与算法细节；
- 完整实验表；
- Prompt、实现和代码结构；
- 作者与机构；
- 投稿与发表信息；
- BibTeX；
- 扩展参考资料。

## 3. 标准正文顺序

方法型、系统型论文默认使用：

```text
30 秒读懂
论文定位
研究问题与动机
进化机制卡片
核心方法
实验设计
主要结论与证据
消融、失败案例与成本
与相关工作的关系
作者结论与我的判断
未解决问题与研究想法
论文外部信息
参考资料与 BibTeX
```

分析、诊断、评测和边界研究用“分析框架卡片”替换“进化机制卡片”。

综述和 position paper 不强制虚构实验章节，应根据论文性质调整，但仍需保留快速阅读层、结论边界和个人判断。

## 4. 30 秒读懂的写法

推荐结构：

```markdown
## 30 秒读懂

> **一句话总结：** 为了解决 X，作者提出或分析 Y，通过 Z 发现 A。

| 维度 | 内容 |
|---|---|
| 文章性质 | 方法 / 系统 / 分析 / 综述 / Position |
| 核心问题 | |
| 核心机制 | |
| 更新对象 | |
| 学习阶段 | 训练时 / 测试时 / 部署时 |
| 是否跨任务 | 是 / 否 / 有条件 |
| 是否更新模型参数 | 是 / 否 / 只更新辅助模块 |
| 最重要结论 | |
| 最大局限 | |

### 不要误读

这篇论文不是……，而是……
```

要求：

- 使用自己的语言，不复制摘要；
- 只写最本质的机制；
- “最重要结论”不等于“主表最高分”；
- “不要误读”应针对该方向最常见的概念混淆。

## 5. 文章定位

这一节必须明确：

- 论文属于哪个方向；
- 论文性质是方法、分析、系统、综述还是立场文章；
- 主要改进发生在哪一层；
- 和仓库中最接近的 2–4 篇工作有什么关系。

对于 Self-Evolving Agent，至少区分：

- 模型参数更新；
- 外部 memory / experience 更新；
- prompt / context / playbook 更新；
- skill / tool / workflow / harness 更新；
- 单任务内 trajectory 搜索；
- Agent 程序或代码自修改；
- synthetic task 生成与训练。

不要只写“属于 Self-Evolving Agent”，因为这不足以定位论文。

## 6. 研究问题与动机

按照三层组织：

1. 当前领域通常怎么做；
2. 现有方法的具体不足；
3. 本文真正要回答的问题。

推荐用一句可检验的问题收束：

> 本文试图回答：……？

避免大段照译引言，避免只写“现有方法存在效率低、泛化差等问题”这类空泛描述。

## 7. 进化机制卡片

方法型 Self-Evolving Agent 论文必须包含：

| 维度 | 内容 |
|---|---|
| 初始 Agent | |
| 学习信号来源 | 成功/失败轨迹、环境奖励、人工反馈、LLM Judge 等 |
| 被更新的对象 | 参数、Memory、Prompt、Skill、Workflow、Trajectory、代码等 |
| 经验形式 | 原始轨迹、规则、案例、向量、程序、权重等 |
| 存储位置 | 当前上下文、文件、数据库、模型参数等 |
| 更新时间 | 每步、每轮、每任务后、离线周期更新等 |
| 后续使用方式 | 检索、拼接、执行、重组、再训练等 |
| 作用范围 | 单任务 / 同分布跨任务 / 长期跨任务 |
| 是否更新模型参数 | |
| 是否需要明确奖励 | |
| 是否依赖教师模型 | |
| 主要计算与 Token 成本 | |

卡片的目的不是重复方法，而是回答“知识如何流动”。

## 8. 分析框架卡片

分析、诊断和边界研究使用：

| 维度 | 内容 |
|---|---|
| 被质疑的常见假设 | |
| 研究对象 | |
| 关键变量 | |
| 控制变量 | |
| 主要诊断指标 | |
| 核心发现 | |
| 结论边界 | |

例如 Harness Updating 论文应明确区分“谁写更新”和“谁使用更新”，而不是只报告最终成功率。

## 9. 方法流程

优先按照信息流或时间顺序组织，不必照搬论文章节。

每个模块应回答：

- 输入是什么；
- 输出是什么；
- 谁执行；
- 什么时候执行；
- 和前后模块如何连接；
- 哪一步是作者新增的；
- 为什么这一设计可能有效。

对于多轮方法，应明确时间索引。例如 MemoPilot 必须说明第 `t` 次 memory update 影响的是第 `t+1` 轮，而不是已经发生的第 `t` 轮奖励。

## 10. 公式和算法

不抄录所有公式，只保留决定方法行为的内容。

每个公式后至少解释：

1. 它在计算什么；
2. 变量表示什么；
3. 在流程中何时使用；
4. 直观上为什么这样设计；
5. 它牺牲了什么或近似了什么。

公式解释应服务于机制理解，不能只把符号翻译成中文。

## 11. 实验设计

实验章节应围绕研究问题组织，而不是按照论文表格顺序罗列。

至少记录：

- 实验对象和 Agent 类型；
- 数据集或环境；
- 基础模型；
- baseline；
- 评价指标；
- 训练或更新方式；
- rollout、调用次数、memory/token budget 等预算；
- 是否使用相同模型和工具；
- 是否依赖 LLM Judge；
- 是否公布统计显著性或置信区间；
- 代码与复现条件。

对比不同论文数字时，必须先确认任务、模型、预算和评测协议是否一致。

## 12. 结论—证据—边界

核心实验论文推荐使用：

| 论文主张 | 支持实验 | 最强对照 | 能证明什么 | 不能证明什么 |
|---|---|---|---|---|

每个重要结论可进一步分为：

```markdown
### 结论

### 论文证据

### 我的判断

### 其他可能解释
```

要区分：

- 作者报告了什么；
- 数据实际支持什么；
- 你的推断是什么；
- 哪些结论仍然不能外推。

## 13. 作者观点与个人判断分离

固定使用清晰标签：

- `作者认为`：忠实记录论文主张；
- `我的理解`：用自己的语言还原机制；
- `我的判断`：评价证据、创新和边界；
- `研究启发`：可迁移到其他问题的设计；
- `未解决问题`：论文没有回答的问题。

不要把个人推断写成论文事实，也不要用“显然”“必然”“证明了所有场景”等过强措辞。

## 14. 创新点

创新点建议分为：

1. 作者声称的贡献；
2. 实际新增的机制；
3. 新发现或新诊断；
4. 与最接近工作的实质差异。

去掉作者命名后，仍应能用普通语言解释新增操作。新术语本身不等于创新。

## 15. 局限性与失败案例

除了论文自述，还应检查：

- benchmark 是否过少；
- 是否依赖特定模型家族；
- 是否依赖强教师或闭源模型；
- 是否只优化当前任务；
- 是否缺少跨任务或跨模型泛化；
- 性能提升是否来自更多 Token、调用次数或搜索预算；
- 是否存在数据泄漏；
- 是否依赖 LLM Judge；
- 是否缺少强 baseline；
- 是否报告方差、置信区间和失败率；
- 动态环境、对抗环境或长期运行是否会退化。

失败案例比泛泛的“未来工作”更有复习价值。

## 16. 成本与复现

方法论文尽量记录：

- 训练模型和执行模型；
- GPU 或 API 依赖；
- 训练数据规模；
- rollout 数；
- 单任务时间预算；
- Token / context / memory budget；
- 是否需要真实环境；
- 是否提供代码、模型、配置和数据；
- 可复现难点。

不能获得可靠成本数据时明确写“论文未报告”，不要估算成事实。

## 17. 作者与机构信息

作者圈子信息有价值，但应放在正文后部。

允许记录：

- 论文首页机构；
- 共同一作、通讯作者；
- 与论文主题直接相关的稳定研究方向；
- 官方个人主页和实验室页面提供的信息；
- 该工作在某条研究线中的位置。

不应：

- 根据机构名称猜测作者具体贡献；
- 根据实习经历推断全部机构归属；
- 使用无法核验的二手履历；
- 为每位作者写与论文无关的长篇传记。

## 18. 图表规范

只保留真正帮助理解的图：

- 总览架构；
- 核心算法流程；
- 最关键结果；
- 最有解释力的消融；
- 典型失败案例。

每张图必须包含：

1. 清晰 alt text；
2. 原论文图号；
3. 来源说明；
4. 一段“这张图最重要的信息是什么”。

图片应嵌入对应章节，不集中堆在开头或结尾。

长期目标是本地化到：

```text
assets/<paper-slug>/figure-1.png
```

外链图片在迁移前应被标记为技术债。

## 19. 链接和 BibTeX

正文顶部只保留最重要资源：

- 论文；
- 代码；
- 项目页；
- 当前状态。

不要在 metadata、顶部、投稿章节和文末重复同一组链接。

BibTeX 放在折叠块中：

```html
<details>
<summary>BibTeX</summary>

```bibtex
@article{...}
```

</details>
```

正式引用信息尚未发布时，应说明当前采用 arXiv BibTeX。

## 20. 文件名与内部链接

- 单篇笔记放在 `notes/`；
- 文件名使用英文小写短横线；
- 尽量与论文完整标题对应；
- `related_notes` 使用仓库根目录相对路径；
- 正文链接使用相对路径；
- 不创建标题不同但内容重复的两篇笔记。

## 21. 文章类型差异

### 方法 / 系统论文

重点：机制、信息流、训练或更新对象、实验、成本、失败模式。

### 分析 / 诊断论文

重点：被质疑的假设、控制变量、诊断指标、替代解释、结论边界。

### 综述论文

重点：分类坐标系、分类之间的边界、覆盖范围、遗漏、对研究路线的组织价值。

### Position / Theory 论文

重点：核心命题、概念定义、规范性主张、可证伪预测、缺失的实证证据。

不要为了模板完整，给没有实验的 position paper 虚构“主实验”。

## 22. 修改和审阅原则

每次 PR 尽量只解决一种问题：

- metadata 规范化；
- 快速阅读层；
- 正文重排；
- 图片迁移；
- 横向综述；
- 自动检查。

批量修改前先用三篇不同类型的论文试点。自动化工具不能覆盖个人判断、研究想法和图的解释。

## 23. 完成检查表

提交新笔记或大幅重构前检查：

- [ ] metadata 符合 `docs/metadata-schema.md`
- [ ] 标题后有“30 秒读懂”
- [ ] 明确更新对象、存储位置和使用方式
- [ ] 明确训练时 / 测试时 / 部署时
- [ ] 明确单任务或跨任务
- [ ] 作者主张与个人判断分开
- [ ] 关键结论有对应证据和边界
- [ ] 记录成本或注明论文未报告
- [ ] 图放在对应内容旁边并有阅读说明
- [ ] 相关笔记路径有效
- [ ] README 和横向综述需要同步更新
- [ ] 外部状态已经核验并更新 `last_verified`
